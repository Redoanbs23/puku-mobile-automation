# End-to-End User Flows

Each flow is written as observable steps. "🟢/🟡/🔴" marks the locator quality of
the element you interact with at that step.

---

## UF-01 · Cold launch → authenticated home (session already stored)

1. Launch app (`sh.puku.app.dev` / `.qa` / `sh.puku.app`).
2. 🔴 `SplashView` spinner (transient).
3. `InitBloc` → `OpenApp`; `TokenManager.getTokens()` returns non-null.
4. `goChatRoot()` → **Chat** replaces the whole stack (no back stack).
5. 🟢 Assert `Key('chatMenuButton')` present. If no history: 🟢 `Key('chatEmptyState')`.

**Sync points:** token read from `shared_preferences` (fast); no network call is
required to reach Chat. Recent conversations load lazily when the drawer opens.

---

## UF-02 · Cold launch → Login (no session)

1. Launch. 2. Splash. 3. `goLoginRoot()` → **Login**.
4. 🟡 Assert text `Continue with Google` and `Enter your email`.

---

## UF-03 · Google sign-in (⛔ hardest flow)

1. On Login, 🟡 tap `Continue with Google`.
2. Route `googleSignIn` pushes; 🟡 AppBar `Continue with Google`, spinner below.
3. **App leaves Flutter**: `FlutterWebAuth2` opens Chrome Custom Tab (Android) /
   `ASWebAuthenticationSession` (iOS) at
   `{AUTH_BASE_URL}/api/oauth/authorize?response_type=code&client_id=…&redirect_uri=…&scope=openid profile email&code_challenge=…&code_challenge_method=S256&state=…`.
4. User authenticates in the browser (Google consent, possibly a
   password + 2FA challenge).
5. Browser redirects to `AUTH_REDIRECT_URI`; Android intent-filters catch either
   `https://api.app.dev.puku.sh/callback` (App Link) or `puku://callback/*`.
6. App validates scheme/host/path, `state` match, non-empty `code`.
7. `AuthBloc` → `POST {AUTH_BASE_URL}/api/oauth/token`
   (`grant_type=authorization_code`, form-encoded).
8. On success: tokens saved, `goChatRoot()` → **Chat**.
9. On failure: 🟡 `Sign in failed. Please try again.` + `Try Again`.
10. On user cancel: route pops back to **Login**.

**Automation strategy:** treat step 3–5 as a context switch (Appium
`NATIVE_APP` → browser package `com.android.chrome`). Strongly prefer
**seeding tokens** (see `automation-readiness.md` §Auth strategies) so most
suites never execute this flow.

## UF-04 · Send a chat message (core happy path) ⭐

**Precondition:** authenticated, on Chat.

1. 🔴 Tap the composer `TextField` (hint `Chat with Puku...`).
2. Type text.
3. 🟢 `Key('chatComposerPrimaryButton')` **appears** (it does not exist while the
   field is empty and there is no attachment). Tap it.
4. Composer clears immediately (`_composerController.clear()`).
5. Send button switches to a `CircularProgressIndicator`; `isSending == true`.
6. 🟢 `Key('chatMessageThread')` renders; user bubble
   `Key('chatMessageBubble_0')`, assistant bubble grows token-by-token as SSE
   chunks arrive; streaming indicator `Key('chatMessageStreamingIndicator')`.
7. Stream terminates on `data: [DONE]`; `isSending == false`.

**Expected results:** user message persisted, assistant reply non-empty,
composer empty, send button hidden again.

**Sync hazards:** the reply is generated by an LLM — duration is unbounded and
content is non-deterministic. Assert on *structure* (bubble count increased,
assistant bubble non-empty) never on wording.

## UF-05 · Attach an image and send

1. 🟢 Tap `Key('chatComposerPlusButton')` → attachment sheet (`Add to chat`).
2. 🟢 Tap `Key('chatPhotosTile')` (or `Key('chatCameraTile')`).
3. **OS picker / camera opens** — outside Flutter. Grant permission if prompted
   (Android `CAMERA`; iOS `NSCameraUsageDescription` / `NSPhotoLibraryUsageDescription`).
4. Back in-app: 🟢 `Key('chatAttachmentPreview')` appears;
   `Key('chatAttachmentRemoveButton')` available.
5. `isUploadingAttachment` blocks send until upload completes.
6. Send as in UF-04.

---

## UF-06 · Browse, search and delete conversations

1. Chat → 🟢 `Key('chatMenuButton')` → drawer.
2. 🟡 Tap `Chats` → **Chats** screen (`ChatsEvent.load()` fires automatically).
3. 🔴 Type into search (hint `Search Chats`) → **wait ≥ 300 ms debounce** before
   asserting the filtered list.
4. 🔴 Long-press a row → selection mode; title becomes `{n} selected`.
5. 🟡 Tap the `Delete` action → dialog `Delete conversations?`.
6. 🟡 Tap `Delete` → row disappears; a SnackBar feedback message may appear.
7. 🟡 Tap `Back` (leaves selection mode first if active, then pops).
8. If the deleted conversation was the active one, Chat resets to a new chat.

---

## UF-07 · Project lifecycle (create → verify → update → delete) ⭐

1. Drawer → 🟡 `Projects`.
2. 🔴 Tap the FAB → Create sheet (title `New project`).
3. 🔴 Fill `Name` (required for `canSubmit`), optionally `Description` and
   `Custom instructions`.
4. 🟡 Tap `New project`; button shows `Creating...` while submitting.
5. Sheet closes; list reloads; SnackBar `Project created`.
6. 🔴 Tap the new row → **Project Details**.
7. 🟡 ⋮ (`More actions`) → `Update project` → edit → `Update project`.
8. 🟡 ⋮ → `Delete` → dialog `Delete project?` → `Delete`.
9. Blocking overlay appears; on completion the screen pops with
   `ProjectDetailsResult.deleted` and Projects shows SnackBar `Project deleted`.

**Best overall E2E candidate** — deterministic, self-cleaning, no LLM in the loop.

---

## UF-08 · Chat inside a project

1. Project Details → 🟡 FAB `New chat`.
2. Chat opens with `startFresh: true, projectId: <id>`; leading button is now
   **back**, not menu (`Navigator.canPop() == true`).
3. Send a message (UF-04) → conversation is created against the project.
4. Back → Chat pops with `ChatScreenResult.projectConversationCreated`;
   Project Details reloads its conversation list and the new conversation appears.

---

## UF-09 · Artifacts

1. Drawer → 🟡 `Artifacts`.
2. 🟢 Assert `Key('artifactsListView')`, or empty text `No artifacts yet`.
3. 🔴 Search (300 ms debounce).
4. Tap a row → **Chat** opens the artifact's conversation.

## UF-10 · Remote session (Code) — full flow

**Precondition:** a `puku-cli` process running `/remote-control` and reachable
by the relay.

1. Drawer → 🟡 `Code` → session list (`GET /v1/sessions?mine=1`).
2. 🟢 Tap `Key('codeNewSessionButton')` (or the empty-state CTA) → **Scanner**.
3. Grant camera permission (first run).
4. 🟢 `Key('remoteSessionScannerView')` shows the preview. Present the QR
   (`puku://remote?s=<sessionId>&t=<token>`).
5. Invalid payload → 🟢 `Key('remoteSessionScannerError')` with
   `Unsupported QR payload. Expected sessionId and token.`
6. Valid payload → route **replaced** by **Remote Chat**.
7. Socket opens `wss://<relay>/client/<sessionId>?token=<t>` with headers
   `X-Puku-Mobile-Token`, `X-Puku-Account-Token`. Relay sends
   `system/reconnect_token`, then `worker_connected`.
8. 🟢 `Key('remoteChatDisconnectButton')` turns green; `canSend == true`.
9. Type a prompt → send (`chatComposerPrimaryButton`).
10. Assistant frames stream in; 🟢 `Key('remoteChatProgressPanel')` shows
    turn/agent progress.
11. When the agent requests a tool: 🟢 `Key('remoteChatPermissionCard')` replaces
    the composer → tap `remoteChatPermissionAllowOnceButton` /
    `remoteChatPermissionAlwaysAllowButton` / `remoteChatPermissionDenyButton`.
12. Optional: 🟢 question wizard (`remoteChatQuestionCard` → `…NextButton` →
    `…SubmitButton`), exit-plan-mode card (`exitPlanModeCard`).
13. 🟢 Tap `remoteChatDisconnectButton` to disconnect, then `Back`.
14. Returning to **Code** auto-refreshes the session list (`RouteAware.didPopNext`).

**Alternative entry:** tap an existing row with `isAvailableToPair == true` —
skips steps 2–6 and needs no camera. **Prefer this path for automation.**

## UF-11 · Change model / permission mode in a remote session

1. In Remote Chat, tap the model chip → sheet `Select model`, options keyed
   `remoteChatModelOption_<model>`.
2. Selecting a different value sends a `control_request` with subtype
   `set_model` and stores `pendingModelChangeRequestId`; while that id is set,
   tapping the chip is routed to a no-op handler until the CLI answers (the chip
   still looks enabled — there is no visual disabled state).
3. Failure → red `SnackBar`.
4. Same pattern for the mode chip (`Key('chatComposerModeChipButton')`, sheet
   `Select Permission Mode`, options `remoteChatModeOption_<mode>`).

---

## UF-12 · Settings → Profile → back

1. Drawer → avatar → **Settings** (🟢 `Key('settings')`).
2. 🟡 Tap `Profile` → **Profile** (`GET /v1/me`).
3. Assert rows `Name`, `Email`, `Sign-in provider`, `User ID` (each optional).
4. Error variant → `Retry` button.
5. 🟡 Back (tooltip/label `Back`).

---

## UF-13 · Logout ⭐

1. Settings → 🟡 `Log out`.
2. Best-effort `POST {API_BASE_URL}/auth/logout` (fire-and-forget).
3. Local tokens cleared, `AuthState.idle`, `goLoginRoot()`.
4. 🟡 Assert `Continue with Google` visible.
5. Kill and relaunch the app → must land on **Login** again (proves persistence
   was cleared).

---

## Recommended E2E suites

| Suite | Flows | Why |
|---|---|---|
| **Smoke** | UF-01, UF-04 (send + non-empty reply), UF-13 | fastest signal on auth, network, streaming |
| **Regression core** | UF-06, UF-07, UF-08, UF-09, UF-12 | deterministic CRUD, no LLM assertions |
| **Remote session** | UF-10 (row-tap variant), UF-11 | needs a live CLI peer — run in a dedicated job |
| **Manual only** | UF-03 (full browser OAuth), UF-05 (camera), scanner QR | external surfaces, device/OS dependent |
